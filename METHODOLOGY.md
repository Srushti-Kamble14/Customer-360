# Splink vs Tilores Benchmark — Methodology

**Last updated:** 2026-06-03 · **Tilores config:** `rule-config.json`

---

## 1. Dataset

Synthetic FEBRL-style dataset, generated by [`benchmark/generate_febrl_data.py`](../benchmark/generate_febrl_data.py):

- **1,000,000 total records** (900k unique entities + 100k duplicate records)
- **Locale:** `en_GB` (UK names, postcodes, phones)
- **Seed:** 42 (deterministic)
- **Ground truth:** [`benchmark/data/ground_truth.csv`](../benchmark/data/ground_truth.csv) — 100,000 known duplicate pairs
- Generator: [Faker library](https://faker.readthedocs.io/) for clean records, custom corruption for duplicates

### Duplicate corruption pattern

For each duplicate, 1–3 random fields from `[first_name, last_name, date_of_birth, street_address, postcode, phone]` get one of:
- character swap (`John` → `Jonh`)
- character delete (`John` → `Jon`)
- character insert (`John` → `Johnn`)
- character replace (`John` → `Jorn`)

10% chance one of `[phone, email, street_address]` is blanked entirely.

`city` is never corrupted (preserved from source) — this enables a key precision optimization (city is used as an exact-match anchor in the Tilores rule config).

### What this is NOT

- ❌ Not the official ANU FEBRL dataset (~5k records, smaller scale)
- ❌ Not Splink's tutorial dataset (`fake_1000`)
- ✅ Synthetic but reproducible, mimics academic FEBRL corruption patterns

## 2. Evaluation Methodology

Both tools evaluate against **all 100,000 ground-truth pairs** (full ground truth file).

### Splink

- Runs full deduplication (1M records → predicted pair list)
- TP = predicted pairs ∩ ground truth
- FP = predicted pairs ∉ ground truth
- FN = ground truth ∉ predicted pairs

### Tilores

- Ingests all 1M records, builds entity index
- For each ground-truth pair (A, B): query `entityByRecord(id=A)`, check if B is in returned entity members
- TP per pair = entity members that ARE in `gt_pairs`
- FP per pair = entity members that are NOT in `gt_pairs` (any spurious co-merge)
- FN per pair = if B not in members

### Why both methodologies are valid

Both compute precision/recall/F1 on the same 100k pairs. Splink uses pair-prediction semantics; Tilores uses entity-membership semantics. The Tilores definition is **stricter on FPs** — if any unrelated record ends up in the queried entity, it counts as FP — while Splink's would only count emitted-pair FPs.

## 3. Tool Configurations

### Splink (default tutorial-style)

[`benchmark/benchmark_splink_febrl.py`](../benchmark/benchmark_splink_febrl.py):
- Backend: DuckDB (recommended for ≤100M records)
- Memory limit: 8GB (measured peak: ~4.9 GB)
- Comparisons: Jaro-Winkler at 0.9/0.7 thresholds on `first_name`, `last_name`, `street_address`; ExactMatch on `date_of_birth`, `postcode`, `city`
- Blocking: `postcode + last_name[:2]` ∪ `dob + last_name[:3]`
- Match threshold: probability ≥ 0.8

### Tilores

[`benchmark/tilores_configs/febrl/rule-config.json`](../benchmark/tilores_configs/febrl/rule-config.json):
- Comparers: `exact`, Cologne phonetic (first name phonetic matching), OSA Damerau-Levenshtein ≥ 0.9 with shingle 4 (fuzzy DOB), Levenshtein distance ≤ 1 (fuzzy name variants)
- 6 linking rules (rs-main):
  - R-EMAIL: email-exact + city-exact
  - R-FN-LN-DOB-CITY: first-name-exact-str + last-name-exact + DOB-exact + city-exact
  - R-FN-LN-DOB-POSTCODE: first-name-exact-str + last-name-exact + DOB-exact + postcode-exact
  - R-FN-LN-DOB-FUZZY: first-name-exact-str + last-name-exact + DOB-fuzzy + city-exact
  - R-LN-FUZZY: first-name-exact-str + last-name-fuzzy (Levenshtein ≤ 1) + DOB-exact + city-exact
  - R-FN-FUZZY: first-name-fuzzy (Levenshtein ≤ 1) + last-name-exact + DOB-exact + city-exact
- `city` used as exact-match anchor in all non-postcode rules — reliable because city is never corrupted in FEBRL data
- Fuzzy DOB rule catches single-character date-of-birth typos via OSA edit distance
- Container: 8GB RAM, 8 cores (measured peak: ~5.7 GB)

## 6. Limitations & Caveats

### Synthetic data
- The 1M dataset is generated, not real-world. Real customer data has different corruption distributions.
- Real FEBRL or DBLP would test different corruption patterns (we tested at scale, they test at <100k).

### Tilores network in this run
- Tilores ran on the same LAN segment as the benchmark host (local deployment)
- Search latency p95 8.6ms — representative of a local deployment
- Accuracy metrics (F1/Precision/Recall) are not affected by network topology

### Splink config not maximally tuned
- Splink's config is the standard tutorial-style for this data type; it is not exhaustively tuned
- A Splink expert could likely squeeze additional 1–2pp F1 with custom blocking and m/u value tuning
- The same applies in reverse: Tilores' config could likely also be pushed higher

### Comparison methodology
- Both tools evaluated on identical 100k ground truth pairs
- Tilores' FP definition is stricter (entity-membership) than Splink's (predicted-pair) — Tilores still won on this stricter metric

## 7. Future Work

Ways this benchmark could be extended for a more complete comparison:

1. **Re-run Splink with equivalent tuning effort** — fair counter-tuning so neither tool's config received disproportionate attention
2. **Run on Splink's `fake_1000` dataset** — adds Splink's own canonical dataset to the validation set
3. **Real customer data sample** — the most credible test, though it would require appropriate data-sharing arrangements
